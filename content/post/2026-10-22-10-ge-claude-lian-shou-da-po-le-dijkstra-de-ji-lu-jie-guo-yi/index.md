评测机构 Vals AI 最近做了一个挺轰动的实验。

他们把 10 个 Claude Opus 5.5 放进同一个沙盒环境，配了一个共享看板和 15 个小时，目标只有一个，看它们能不能联手推导出一个渐进复杂度优于经典 Dijkstra 的单源最短路径算法，并且给出形式化数学证明。

这 10 个模型在沙盒里发了 733 条长消息，互相推导定理、挑刺、构造反例，最后还真捣鼓出一个叫 C-HD 的新算法。

![玻璃沙盒里十个橙色小机器人围着贴满便签的共享看板，有的钉便签，有的拿放大镜审稿，有的画红叉，角落里还有一个抱着咖啡睡着了](https://xiaobox-public-images.oss-cn-beijing.aliyuncs.com/images/dijkstra-%E5%9B%BE1-%E5%8D%81%E4%B8%AA%E6%9C%BA%E5%99%A8%E4%BA%BA%E6%B2%99%E7%9B%92%E5%8D%8F%E4%BD%9C.png)

更绝的是，它们不仅写出了伪代码，还用数学证明语言 Lean 4 给出了完整的形式化机器证明，且被编译器严格跑通。在特定密度的稀疏图里，这套算法的理论渐进复杂度上界，确实压过了 Dijkstra 统治几十年的经典纪录。

消息一出来，在技术圈引起了不小的讨论，不少人以为经典理论要被改写了。

但 Vals AI 自己在报告里就写明了，他们没在大规模真实图上跑过测试，证明里的常数巨大，不代表实际能提速。

随后，日本开发者 mizchi 照着论文用 Rust 把 C-HD 完整实现了一遍，拉去和 Dijkstra 对比。从 1.6 万个节点一路测到 419 万个节点，C-HD 每一档都输给了 70 年前的经典 Dijkstra，算上预处理慢了 1.47 到 7.3 倍，扣掉预处理只比核心部分，也还慢 1.12 到 3.9 倍。

为什么理论上超越了经典的算法，在真实跑分里反而会慢上几倍？

要看清这场测试到底发现了什么，我们得先回到寻路问题的起点，在计算机眼里，到底是怎么在一张地图上找路的。

## 寻路算法的唯一母体，波前扩张

不管是《红色警戒》里一辆坦克的走位、高德地图里为你避开拥堵的实时导航，还是 Linux 内核里一个数据包的路由，计算机面对一张复杂的地图时，根本没有人类那种纵观全局的「天眼」。

它所能做的唯一一件事，就是在黑暗中以起点为中心，向外画一个不断膨胀的圈。

在路径规划与图形学中，这个从起点向外推进的过程通常被称为 **「波前扩张（Wavefront Expansion）」** 而在代码里，维护这道扩张边缘的数据结构，通常叫 **「探索前沿（Frontier）」**。

以最基础的无权图或网格地图为例，从起点开始寻找一条路径，代码可以写得很精简，

```python
frontier = Queue()
frontier.put(start)
reached = set()
reached.add(start)

while not frontier.empty():
    current = frontier.get()
    for next in graph.neighbors(current):
        if next not in reached:
            frontier.put(next)
            reached.add(next)
```

这就是标准的广度优先搜索（BFS）。

从起点出发，将相邻的未访问邻居推入普通队列；随后按先进先出的顺序依次出队，继续扩展下一层邻居。探索波前像同心圆一样，均匀向外一圈圈推开。

但上面的代码只完成了「全图遍历」，并没有记录走过的具体路径。

要获取最终路径，只需要在遍历的同时记录每一个节点的前驱节点，也就是在代码里维护一个 `came_from` 字典，记录「我是从哪个邻居走过来的」，

```python
frontier = Queue()
frontier.put(start)
came_from = dict()
came_from[start] = None

while not frontier.empty():
    current = frontier.get()
    if current == goal:
        break

    for next in graph.neighbors(current):
        if next not in came_from:
            frontier.put(next)
            came_from[next] = current
```

当探索前沿触及目标点（`goal`）时，循环立刻停止。

此时从终点出发，沿着 `came_from` 中记录的前驱指针一路倒推回到起点，再将序列反转，得到的就是起点到终点的最短路径。

## 当地图有了权重，Dijkstra 诞生了

广度优先搜索能找到最短路径的前提，是每一步的移动代价完全相同。此时「步数最少」就等于「总代价最低」。

但现实中的网络和地图很少是等权的。

在道路交通里，高速路与泥泞小道的通行时间截然不同；在通信网络里，光纤专线与跨洋卫星的延迟相差百倍；在游戏地形中，平原与沼泽的移动消耗也各不相同。

一旦边的权重有了差异，步数最少的路线往往不再是总成本最低的路线。

![提灯到小旗之间隔着一片沼泽，走直线的小人陷在泥里拖着漏金币的大钱袋，走上方橙色绕路的小人背着小包哼着歌](https://xiaobox-public-images.oss-cn-beijing.aliyuncs.com/images/dijkstra-%E5%9B%BE4-%E7%9B%B4%E7%A9%BF%E6%B2%BC%E6%B3%BDvs%E7%BB%95%E8%B7%AF.png)

这就是 1956 年摆在年轻程序员 Edsger Dijkstra 面前的难题。

那一年，26 岁的 Dijkstra 陪着未婚妻去阿姆斯特丹买衣服。未婚妻在商场挑裙子，他坐在咖啡馆的露天长椅上喝咖啡。为了给荷兰一台叫 ARMAC 的老式计算机设计一个向公众演示性能的小程序，他在没带纸、没带笔的情况下，只花了 20 分钟，在脑子里彻底重构了寻路的波前。


Dijkstra 做的事情，在代码层面只改动了两个极度关键的细节，

第一，将原本先进先出的普通队列，替换为**优先队列（最小堆 Min-Heap）**。
第二，在每个节点上挂一个 `cost_so_far` 字典，记录从起点走到这个点已知最小的累计成本。

```python
frontier = PriorityQueue()
frontier.put(start, 0)
came_from = dict()
cost_so_far = dict()
came_from[start] = None
cost_so_far[start] = 0

while not frontier.empty():
    current = frontier.get()

    if current == goal:
        break

    for next in graph.neighbors(current):
        new_cost = cost_so_far[current] + graph.cost(current, next)
        if next not in cost_so_far or new_cost < cost_so_far[next]:
            cost_so_far[next] = new_cost
            priority = new_cost
            frontier.put(next, priority)
            came_from[next] = current
```

循环中那行条件判断 `if next not in cost_so_far or new_cost < cost_so_far[next]`，就是算法中著名的「松弛（Relaxation）」操作。

它的逻辑很简单，比较经过当前节点到达 `next` 的累计成本是否优于已有记录。如果找到了更便宜的走法，就更新账本并把更低代价的节点加入优先队列。

Dijkstra 算法的正确性，建立在它的 **贪心不变量（Greedy Invariant）** 上，

**只要一个节点从最小堆里出堆，它到起点的最短距离就已经确定，后续不需要也不可能再次更新。**

这个性质能成立，依赖一个刚性前提，图中所有边的权重必须非负（$\ge 0$）。

因为当前出堆的节点，在所有已发现但未锁定的候选点里累积代价最小。既然未来每多走一步成本都只增不减，那么通过其他任何分支绕一圈再来到这个节点，累计花费必定严格大于当前值。

这种单调性保证了它不需要回溯，每一步都稳步扩大确定区域。正因如此，它在 OSPF、IS-IS 等互联网骨干路由协议里平稳运行了几十年。

## 加上方向感，为什么点对点导航需要 A*

Dijkstra 解决的是「单源全图最短路径」，也就是从起点到图上**所有节点**的距离。

但现实中的导航需求，绝大多数是精确的点对点寻路，从当前位置开往特定终点。

如果拿 Dijkstra 直接做点对点寻路，会产生巨大的无效搜索。因为优先队列的排序依据只有一个，从起点出发已经花掉了多少成本（$g(n)$）。它对终点在哪个方向没有任何感知。

假设要从北京开车去上海，终点在东南方。但由于缺乏目标指引，Dijkstra 的波前会以北京为圆心，向四面八方对称扩散。它在向南搜索济南的同时，会以完全相同的优先级向北排查张家口、向西搜索呼和浩特。

在一张数千万节点的真实路网图上，这种无方向的全域扩散会极快消耗内存和计算时间。

要让搜索波前产生方向感，就需要在评估节点时把「终点的距离」也算进去。

1968 年，斯坦福研究所的 Peter Hart、Nils Nilsson 和 Bertram Raphael 提出了一个经典方程，

$$f(n) = g(n) + h(n)$$

这就是 **A\* 算法**。

对比 Dijkstra，代码核心改动其实只有一处，把优先队列的排序权重从单纯的累积成本，换成了综合预估值 $f(n)$，

- $g(n)$，依然是 Dijkstra 记录的，**从起点走到当前点的已知实际代价**。
- $h(n)$，是启发式函数（Heuristic），**从当前点到终点的预估剩余代价**（例如网格地图上的曼哈顿距离或欧几里得直线距离）。
- 优先队列里的优先级，按两者的和 $f(n)$ 排序。

引入 $h(n)$ 之后，原本向四面八方均匀扩散的圆形波前，被引导着偏向终点方向延伸。背离终点方向的节点，由于预估剩余距离过大，在优先队列中被排到靠后的位置；朝着目标前进的节点则被优先探索。

![左边 Dijkstra 以天坛为圆心向四面八方照亮一整圈，草原毡房和海面都照到了，圈的边缘才碰到东方明珠，右边 A* 的光像一滴泪，从天坛收窄着一路指向东方明珠](https://xiaobox-public-images.oss-cn-beijing.aliyuncs.com/images/dijkstra-%E5%9B%BE6-%E5%A4%A9%E5%9D%9B%E5%88%B0%E4%B8%9C%E6%96%B9%E6%98%8E%E7%8F%A0Dijkstra%E5%AF%B9%E6%AF%94Astar.png)

只要启发式估计 $h(n)$ 满足可采纳性（Admissible，即估算值永远不超过实际真实最短距离），A\* 就能在数学上保证找到最优路径，同时大幅削减无用的探索节点。

从《星际争霸》里的兵种跑位，到《赛博朋克 2077》的 NPC 导航，现代数字世界里绝大多数的实时寻路，跑的全是 A\* 及其各种工程变种。

## 那么，10 个 Claude 到底打破了什么纪录？

把这套寻路的进化谱系在脑子里建立起来之后，我们终于能回过头来看这次轰动全球 AI 圈的实验了。

既然人类的寻路体系已经如此严密成熟，那 10 个被关在沙盒里的 Claude Opus 5.5，究竟是在哪里找到了突破口？

它们既没有推翻贪心思想，也没有改写 A\* 的启发式逻辑。

它们真正优化的，是优先队列本身的维护瓶颈。

在经典 Dijkstra 算法里，每探索一条边，就可能要把一个节点推进最小堆，或者在堆里更新一次它的优先级。如果一张图有 $n$ 个节点和 $m$ 条边，频繁的堆操作会把整体时间复杂度落在 $O(m + n \log n)$。

几十年来，理论计算机界尝试过斐波那契堆等各种精巧的数据结构，试图把那个对数项 $\log n$ 往下削减。

这 10 个模型在沙盒里推演了 700 多轮，交出的 C-HD 并不是从零发明，它沿用的是 2025 年清华段然团队那篇拿了 STOC 最佳论文的「打破排序壁垒」路线。

Dijkstra 慢就慢在它要把所有候选节点按距离排得清清楚楚，每次都精确取出最近的那一个，这一排就绕不开 $\log n$。段然团队的思路是干脆不排全序，把距离切成一段一段的区间，每段里先用几轮类似 Bellman-Ford 的松弛找出少数「关键节点」，再递归去处理规模更小的子问题，一批一批地把距离定下来。

C-HD 在这套递归框架上又改了几处细节。先把每个节点的出边数压到一个上限以内，把邻接表提前排好序，再用指针顺序往下扫，让每条边在整条递归链里只被扫一遍。

在特定密度的稀疏图上，它们从数学上推导出了 $O(n \log^{11/12} n)$ 的渐进复杂度上界。

更有价值的是推导的严谨度。它们不仅写出了算法逻辑，还用形式化证明语言 Lean 4 输出了一套包含 289 个证明文件的定理包，所有引理与边界条件全部通过了编译器的机器验证。

从理论计算机科学和自动化科学发现的角度来看，这确实是一次高质量的实验。它展示了大模型在多智能体协作与形式化验证工具配合下，已经具备推演复杂数学定理的能力。

## 银河算法，理论最优与工程实用的鸿沟

那么，生产环境里的 Linux 路由栈、高德地图、游戏引擎，会因此淘汰掉 Dijkstra 和 A\* 吗？

答案是，几乎不可能。

在算法理论界，有一类被称为 **「银河算法（Galactic Algorithm）」** 的特殊存在。

所谓银河算法，是指它在数学的大 O 渐进复杂度上确实更优。当数据规模 $n$ 趋近于无穷大时，它的理论耗时最终一定会比经典算法更少。

但大 O 记号在渐进分析时，为了凸显函数增长趋势，抽象掉了表达式前面的**常数项 $C$** 以及低阶初始化开销。

现实系统中真实的运行时间，从来不是单纯的 $O(f(n))$，而是 $C \times f(n) + \text{常数开销}$。

经典 Dijkstra 的常数项极小。它的核心循环只有简单的数组访问、哈希查找与基础二叉堆调整，内存访问模式连续，对现代 CPU 的缓存行非常友好。当年 Dijkstra 设计它时，首要目标就是让它在老式计算机 ARMAC 有限的内存和磁鼓里，用最少的指令跑出结果。

<!-- 可选原始图，Dijkstra 本人 1994 年在苏黎世 ETH 讲课，用的话图下须加一行署名「图源 Wikimedia Commons，Andreas F. Borchert 摄，CC BY-SA 4.0」: https://xiaobox-public-images.oss-cn-beijing.aliyuncs.com/images/dijkstra-%E5%8E%9F%E5%A7%8B%E5%9B%BE-1994%E5%B9%B4ETH%E8%AE%B2%E8%AF%BE.jpg -->

而 C-HD 为了撑起那套递归框架，要给每个节点打上五元组标签来做比较，要先把所有邻接表排一遍序，还要维护分块结构和找关键节点用的临时树，每一步都在往常数项上加码。mizchi 专门数了比较次数，C-HD 平均每条边要比 12 到 19 次，Dijkstra 只要 3.6 到 8.5 次。

反过来看理论上能省下的部分，只有 $\log^{1/12} n$ 这么一点。到 419 万个节点时也才 1.29 倍，就算放到 Vals AI 博客里举的 $n = 2^{1000}$ 这种天文规模，也只有 1.78 倍。拿这点理论优势去填好几倍的常数差距，根本填不上，实测里也看不到任何追上来的迹象。要让它真正追平，所需要的图节点规模将远超现实工程能够触及的极限。

Vals AI 的这次测试，是一次高质量的理论计算机科学与自动化定理证明实验。它证明了大模型在形式化工具的约束下，已经具备推演复杂前沿数学定理的能力。

但工程和理论是两套完全不同的评价体系。理论在象牙塔里追求 $n \to \infty$ 时的渐进极限；而在物理世界的服务器里，决定一行代码能否长久跑下去的，往往是极简的数据结构、极小的常数项，以及对硬件足够友好的内存布局。
