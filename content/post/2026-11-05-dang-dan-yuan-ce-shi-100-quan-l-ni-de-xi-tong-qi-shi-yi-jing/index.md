现在用 `Claude Code` 或者 `Cursor` 写代码，最爽的瞬间，莫过于看着终端里一排排单元测试刷出清一色的绿勾。

以前要折腾两三天的需求，现在把提示词丢给 Agent，喝口水的功夫，合并请求就提上来了。点开一看，代码格式极其工整，变量命名挑不出毛病，旁边的两百多个单元测试全部通过。

面对这样一份赏心悦目的代码，很少有人还能忍住不点通过。花十秒钟扫一眼，手指一抖就合进了主干。

可等到几周后线上某个边缘场景突然报错，需要有人去改这段逻辑时，荒诞的一幕就会出现。你把那段漂亮的代码翻出来盯了半小时，突然发现**整个团队里，竟然没有一个人能解释清楚这段代码当初为什么要这么写。**

它就这么安安静静地躺在生产环境里，跑是能跑，但谁也不敢乱动。

这两天，`Anthropic` 旗下 `Claude Code` 团队的核心工程师、前谷歌 `Chrome` 工程主管 Addy Osmani 发了一篇长文，在技术圈引发了刷屏讨论。他在文章里给这种新型工程绝症起了个精准的名字，叫**「理解债」（`Comprehension Debt`）**。

过去几十年，程序员最怕的是「技术债」。前人为了赶进度写出一堆屎山代码，结构混乱、耦合极深。但技术债有个好处，它闻起来是臭的。你一打开文件就能看到满屏警告，改一行崩三处，那种强烈的摩擦感会时刻提醒你这地方早晚要还债。

可 Agent 时代的「理解债」完全反过来。**它是香的，甚至自带极强的欺骗性。**

代码看着比资深工程师手写的还干净，提交记录井井有条，测试通过率百分之百。但在硬盘里代码行数暴涨的同时，人类大脑对这套系统的理解程度却在原地踏步。

为什么连经验丰富的老程序员，看到「测试全绿」都会不由自主地放下戒心？

沃顿商学院的学者 Steven Shaw 和 Gideon Nave 今年在论文里把这种心理拆解得很透彻。卡尼曼曾把人类大脑分成直觉快思考的「系统 1」和深度慢思考的「系统 2」，而今天的大模型已经成了长在人脑外面的「系统 3」。

以前我们用计算器算账，叫「认知卸载」，活让工具干，但账本逻辑还在自己脑子里。现在面对反应极快、吐字极自信的 Agent，人脑为了省力，极容易滑向另一个状态，叫**「认知投降」（`Cognitive Surrender`）**。

更隐蔽的陷阱在于，当你让同一个 Agent 既写业务代码、又顺手把单元测试也写了的时候，你其实是在让它**左手写 Bug，右手给自己发合格证**。

大模型写的单元测试，测的根本不是真实的业务边界，而是把刚才生成代码时的错误假设又复述了一遍。两百个绿勾，只能证明它成功地自圆其说了两百次，那些它压根没想到的极端异常，连进测试名单的机会都没有。

![同一个机器人给小车装上方轮，又给它盖了合格章](https://xiaobox-public-images.oss-cn-beijing.aliyuncs.com/images/comprehension-debt-self-certified.png)

读到 Addy Osmani 的这段分析时，我立刻想起了四十一年前的另一篇计算机经典。

1985 年，图灵奖得主 Peter Naur 写过一篇著名的论文，叫《编程即理论构建》（`Programming as Theory Building`）。老爷子在四十一年前就下过一个论断，**软件的本体，根本不是存在硬盘里的那几万行源代码，而是长在程序员脑子里的那套「系统理论」。**

他在论文里指出，如果把某个软件的全部源代码和文档完整保留下来，但把当初写这套系统的原班程序员全换掉，再招一群同样优秀的程序员接手，这个软件其实就已经死了。新团队面对任何稍微复杂的改动，都只能在外面糊一层又一层难看的补丁，因为那套关于「系统为什么长这样」的活体记忆，已经随着老团队的离开彻底消失了。

![机器留在原地，走出门的工程师带走了心里的那张系统图](https://xiaobox-public-images.oss-cn-beijing.aliyuncs.com/images/comprehension-debt-mental-map.png)

过去手写代码之所以慢，是因为人在敲键盘、调错、抓狂的煎熬过程里，顺便在自己脑子里把这套「系统理论」给长出来了。

今天 Agent 把写代码的时间从三天压缩到了三分钟，也把逼着人动脑子的那段摩擦期抽干了。仓库里的代码量蹭蹭往上涨，但团队里却没有一个人真正走完过「理论构建」的过程。**这些代码从合进主干的第一天起，就成了没人敢认领的遗留代码。**

那怎么才能既用上 Agent 的速度，又不把脑子彻底交出去？Addy Osmani 在文章里聊了几个他自己日常在用的土办法，其实特别好上手。

最简单的一条，是在敲回车把需求丢给 Agent 之前，自己先花半分钟想一下，这事要是让我自己改，大概会动哪几个文件，核心逻辑在哪一层。哪怕只在备忘录里记两三个词也行。只要脑子里先有了个底，等 AI 把几百行代码吐出来的时候，你就立刻能看出来它是不是又绕远路了，不至于顺着它的思路一路点头。

到了审代码准备合并的时候，也有个很好使的办法。别去问 AI「这段代码有没有问题」，你这么问，它十有八九会跟你说没问题。你可以反过来问它，「假设这段代码上线之后挂了，你觉得最可能是哪个前提条件没兜住？如果我要验证这个风险，该补一个什么样的测试？」

甚至遇到核心模块的大改，你还可以让 Agent 反过来考你一下，让它根据刚写完的改动给你提三个问题，看看自己能不能不看代码答上来。比如：“现在你是严厉的面试官，针对你刚才改的逻辑，出三道刁钻的边界题考我，我答不上来就不准合并。”

要是连它随口问的边界情况都答不上来，那就说明这笔「理解债」已经欠下了，这时候真不能急着点合并。

毕竟代码是谁写的并不重要，到了做代码审查、在合并按钮上点下去的那一刻，签字画押的人还是你自己。连自己都讲不明白的代码，真别往主干里合。
